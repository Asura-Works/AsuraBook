# 18 実装順序・リリース条件

版1.0 / 2026-10-23。段階は依存関係に基づく。固定の完成日・外部契約費用は未確定。

## 1. 最初の実証で調べること

Python3.13/uv/PySide6のWindows組合せ、SQLite実行版、named pipe、exe起動、Claude画像とJSON、Codex非対話、認証mode、クラウドupload、対象銀行CSVを小さい縦通しで確認する。

カードAPIの契約可否とe-Tax年版/形式はM0から確認を始める。大量の画面を作った後に、必要な接続が利用不能と判明する進め方を避ける。

## 2. マイルストーン

| 段階 | 実装範囲 | 完了に必要な証拠 |
|---|---|---|
| M0 | runtime、IPC、AI、upload、実資料確認 | Windows実機、実画像、対応CLI/auth、対象CSV、外部条件一覧 |
| M1 | 会計核、GUI/CLI、銀行CSV、証憑、Claude、cloud、backup | 貸借・不変性・再取込・原本復旧・GUI/CLI一致 |
| M2 | 5サービスadapter、N:M消込、訂正、年度跨ぎ | サービス別原本照合、月次→明細移行、売掛/入金一致 |
| M3 | カードAPI、制度監視、申告監視、日常運用 | 対象カード実取得、認可/失効、一次資料差分、AI結果不明回復 |
| M4 | 決算・年版税務・帳票・E1/E2 | 同年公式資料との一致、対応範囲、公式ソフト読込/受付管理 |
| M5 | スマホ受付、追加税務、必要ならE3 | 追加範囲の個別受入条件を満たす |

M1のcloud原本保管とClaude画像読取りはユーザーの主要要件として含める。単なる手入力会計だけを最終完成とはしない。

## 3. 会計核を先に固定する理由

仕訳不変性、原本/観測/経済イベントの分離、訂正グループ、source利用枠、open_item_id、日付付き割当、証憑多索引、idempotency、audit/outboxは後の全機能の基盤。

特に年跨ぎや訂正を後付けするために、初期データを破壊的に作り直す設計は避ける。M1時点でモデルを持ち、M2で画面とadapterを拡げる。

## 4. リリースゲート

G0: 採用runtimeと依存をlock。Windows実機で起動。
G1: 会計の不変条件・同時要求・idempotency・snapshotが成立。
G2: 原本取込/保存/再取得/復旧が成立。
G3: Provider実接続とAIの制限・実効認証・quota/unknownが成立。
G4: 対応税年の公式資料・様式・適用日を検証。
G5: 配布、移行、backup、新PC復旧、使用説明を検証。

未対応Provider・税目・年版を機能旗で隠して対応済みにしない。状態を「未設定」「実資料検証待ち」「本番利用可」と分ける。

## 5. 年次更新の工程

監視で変更候補を発見→一次出典確認→対象年/取引日/条件を確定→ruleと帳票差分→境界値fixture→前年回帰→公式出力照合→人の承認→版公開。

前年snapshotは旧rule/入力を保持する。新しい法令が施行されても過年度帳簿と申告を勝手に再計算しない。AIは差分理解・テスト案の補助を行い、本番ruleの無審査更新はしない。

## 6. 外部待ちの扱い

銀行・カード・サービスの匿名化実サンプルがない場合はadapterの本番化を止め、共通CSV/手入力でcoreを検証する。APIが契約できない場合は「自動取得未達」を残し、ユーザーが代替運用を選べる。

e-Tax直接送信が利用できなくても、正式な.xtxを公式ソフトへ渡すE2でオンライン提出を実現できる可能性がある。対象年・税目・書類の読込を実証して採用する。

## 7. 運用費と保守

費用項目はAI契約/利用量、金融データProvider、object storage/転送/backup、gateway、署名配布、保守。サービス価格は変わるため金額を設計書へ固定せず、契約前に実見積を取る。

監視頻度、画像の派生数、再読取、完全backup頻度を設定し、使用量・前回成功・失敗理由を可視化する。上限到達時は本人確認や待機へ戻し、別の課金経路へ無断で切り替えない。

## 8. 開発成果物

各段階で、実装、migration、契約schema、fixture、期待値、受入結果、操作手順、既知の未対応、復旧手順を揃える。設計書のSQL/JSONが読み込めたことと、アプリが業務利用可能なことを区別して報告する。
