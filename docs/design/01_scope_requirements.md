# 01 要件・対象範囲

版1.0 / 2026-10-23。製品仮称TaxDesk。これは新規アプリの詳細設計であり、完成したアプリの操作説明ではない。

## 1. 確定した要件

| 項目 | 採用要件 |
|---|---|
| 操作環境 | Windows 11 x64 |
| 言語・環境 | CPython 3.13、uvによる仮想環境・依存固定 |
| GUI | PySide6 |
| 会計データ | ローカルSQLite |
| AIからの操作 | taxdesk CLI、JSON入出力 |
| アプリからのAI利用 | claude -p、codex exec |
| レシート | Claudeを標準に画像認識、原本をクラウドへ保管 |
| 売上元 | ランサーズ、ココナラ、MENTA、クラウドワークス、note |
| 到達目標 | 記帳、決算、申告書作成支援からe-Taxオンライン申告 |

「クラウドソーシング」はクラウドワークスを指すことが確認済み。スマホ専用アプリは将来であり、初期は撮影済み画像をWindowsへ渡す。

## 2. 設計上の仮定

国内の個人事業主1名・1事業者・JPY・事業所得を中心にする。複数年度を1DBで管理し、一般用の青色申告決算を主な想定とする。ただし利用者が青色承認済み、消費税免税、インボイス未登録等であるとは決めつけない。これらは初期税務設定で確認する。

給与・年金等の他所得、所得控除、家族情報は帳簿だけで判明しないため、申告情報として別入力する。複数事業者の同時利用、法人税、農業、複雑な分離課税、非居住者、外貨自動換算は初期完全対応の対象外。未対応条件を検出したら、必要集計を出し公式作成コーナー等で補完できる。

「新しい商法」は制度変更監視を主に想定する仮定。商売手法の調査を意味する場合も、公開情報topicとして追加できる。

## 3. 機能要求と完了条件

| ID | 機能 | 完了条件 |
|---|---|---|
| FR01 | 毎日の仕訳表 | 複合仕訳、検索、訂正履歴、貸借検証、CSV/PDF |
| FR02 | 元帳・試算表 | posted仕訳だけを集計し残高が一致 |
| FR03 | カード自動取得 | 契約・認可済みAPIから対象カード実明細を取得 |
| FR04 | 銀行CSV | 選んだ銀行の実サンプルで列・符号・日付・残高を検証 |
| FR05 | 5サービス売上 | 総額・手数料・源泉・振込を意味別に取り込む |
| FR06 | 画像受付 | 原本不変、再投入の重複判定、読取り位置への逆引き |
| FR07 | Claude画像読取り | 実画像を読みschemaへ抽出し、手修正できる |
| FR08 | クラウド保管 | 保存versionとhashを確認し未同期を区別 |
| FR09 | 照合 | 売上と入金、カード購入と引落しを二重計上しない |
| FR10 | 決算整理 | 家事按分、資産、前払・未払、源泉、年跨ぎを確認 |
| FR11 | 申告資料 | 対応年版で集計・帳票・転記ガイドを再現可能に作成 |
| FR12 | e-Tax | 対応年の正式形式と公式ソフトで送信まで確認 |
| FR13 | 状況確認 | 残高・損益・取得不足・未確定・証憑不足・申告進捗 |
| FR14 | CLI | GUIと同じサービス・権限・検証を使用 |
| FR15 | 保全 | 一貫backupと新PCへの復旧を検証 |
| FR16 | 法令監視 | 一次出典・適用日・案/成立/施行を分離 |
| FR17 | 申告監視 | 数値検査とAI説明から根拠付き対応項目を提示 |
| FR18 | AI実行管理 | 認証、上限、中断、結果不明、利用量を追跡 |

CSVを利用者がダウンロードして渡す方式は、APIによるカード自動取得の代替経路。API取得の完了条件をCSVだけで満たしたことにはしない。

## 4. 最初から守る品質条件

金額は円整数。比率・中間計算はDecimal。posted仕訳は不変で、訂正は反対と置換を追加する。原本・観測・経済イベント・仕訳を分離し、同じ資料を再取得しても記帳が増えないようにする。

UIの応答、通信、画像解析、帳票出力を分離して画面を固めない。オフラインでも既存帳簿の閲覧と手入力を行える。外部取得・Claude・クラウド同期は待機状態を明示する。

初期の性能目標は、通常の画面操作の応答を100ms程度で開始、10万仕訳規模で日付索引検索を概ね1秒以内。目標値であり未測定。採用端末・日本語path・DPI・ウイルス対策ソフトを含め実機で評価する。

## 5. 段階的な完成

M0: 技術と外部接続の実証。
M1: 会計核、手入力、対象銀行CSV、Claude画像読取り、クラウド原本、backup。
M2: 5サービスの確認済み取込とN:M照合。
M3: 契約済みカード自動取得、制度・申告モニタリング。
M4: 対応年の決算・申告帳票、E1/E2によるオンライン申告。
M5: スマホ受付、必要ならE3直接送信、追加税務範囲。

M0でカード契約とe-Tax形式を調べる。依存関係が大きいため、後半まで可否確認を先送りしない。

## 6. 実装前に具体化する設定

利用銀行・口座種別・CSV、カードブランド/発行会社/契約、各売上サービスの契約区分と匿名化サンプル、対象申告年、青色申告承認、消費税・インボイス状況、他所得、既存残高、クラウド保管先・費用上限を設定する。未確定でもcore設計は進め、当該adapterや税務機能の本番化だけを保留する。

TKCの機能は比較参考とし、その認証・税務対応・既存連携を自作アプリが自動的に継承するとは扱わない。

参考: https://www.tkc.jp/fx/ 、https://www.tkc.jp/fx/fintech/ 、https://www.tkc.jp/fx/tds/ （確認日2026-10-23）。
